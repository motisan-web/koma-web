# Koma Web 設計ドキュメント

---

## Part 0 | 現状のKoma web

### 0-1. 概要

Koma webはもちさんが自作したWebベースの作業管理ツール。シンプルな構成で、実装・改修はAIコーディング（Opus＋Codex）で朝食中に完了するレベルのコストで行える。

### 0-2. 現状の機能

- 1日6コマのタイマーが並んで表示される
- コマごとに個別タイマーがある
- コマ枠は追加可能（イレギュラー対応）
- 1日6コマ使うことを目標に運用している
- コマの進捗状況を入力する形式

### 0-3. 現状の課題・未実装

- 全体進捗の%表示がない
- 就寝時刻管理・カウントダウンがない
- 経験値・ゲーミフィケーション要素がない
- スタートアップフローがない
- UXが発展途上

### 0-4. 関連ツール構成

| ツール | 役割 |
|---|---|
| Koma web | コマ進捗管理（本ドキュメントの対象） |
| Moti tool | 全行動データの入力・記録（自作、改修コスト高め） |
| Obsidian | 日次記録・情報管理・ダッシュボード（コマデータと同期） |

## Part 1 | 思想・意図・背景

### 1-1. 出発点：「忙しい」という認知の廃止

このツールの設計思想は、**認知ラベルが行動を支配する**という観察から始まっている。

「忙しい」と認識すると、以下のループが発生していた。

```
忙しいと認識する
→ 先取りしようとする
→ 1日が後ろ倒しになる
→ リズムが崩れる
→ ミスが増える
→ 実質的な作業時間が伸びる
→ さらに忙しくなる（ループ）
```

この自己強化ループの入口にある「忙しい」という認知ラベルを外すことで、チェーン全体が起動しなくなった。また、休みの前日だけ「忙しいを廃止する」という局所的な適用を試みたところ、**完了の境界線が引かれ、休日を休日として使えるようになった。**

> やりきったかどうかは客観的な事実ではなく、認知の問題だった。

---

### 1-2. 操作コストがやらない理由になってはならない

「やるべきだとわかっている」タスクが、「ツール上での操作が面倒」という理由で実行されないのは設計の失敗である。

ツールは行動を記録するためにあり、記録のためにツールを開く手間が行動の障壁になってはならない。

**NFC連携の意図：**
定期タスクにNFCタグを物理的に紐づけることで、タグを読み込むだけでタスクの実行が記録される。例えばゴミ箱にNFCを貼っておき、ゴミをまとめる際に読み込むだけで「ゴミ捨て完了」が記録されxpが付与される。

- Koma webを開く必要がない
- タスクを検索する必要がない
- チェックを押す必要がない

これはタスク実行APIを外部から叩ける設計と直接対応している。NFCはそのAPIの最もシンプルなクライアントである。

周期が来ていないタスクや、突発的に発生したタスクも同様に記録できる。「今やった方がいい」という判断をした瞬間に、記録の手間ゼロで消化できる状態を目指す。

---

### 1-3. 核心原則：認知設計を意志力ではなくツール側に外注する

「頭の中で唱える」「意識を変えようとする」という方法は、実行にコストがかかる。

**ツール側にその認知があらかじめ組み込まれていれば、意識しなくても実行される。**

- 壁に言葉を張り出す
- ツールに表示しておく
- チェックボックスを置く

これらはすべて「意志力への依存をゼロにする」ための外部化手段である。Koma webはこの原則に基づいて設計される。

---

### 1-3. 「時間が足りない」問題の再定義

時間が足りないという表現には構造的な違和感がある。

- 今日設定した作業だけをこなすなら：足りる
- やりたいことを全部こなすなら：構造的に永遠に足りない（生成速度 > 消化速度）

**問題は時間の量ではなく、今日の範囲をどこで区切るかの設計にある。**

Koma webはこの「今日の範囲の境界線」を、ツールとして可視化・確定させる役割を担う。

---

### 1-4. 1日を始める前のシミュレーションの重要性

1日を具体的に想像して設計すると、集中力が上がり余計な行動が減るという知見がある。

- やることを羅列し、優先順位をつける
- 目を閉じて、それをこなす自分を想像する
- 時計がどれだけ進むかを予想する
- コマごとに何をやるかを設計する

**この工程はKoma webの中で最も大切にすべきプロセスである。**
意識的にやらせるためのチェックと、サボれない導線設計が必要。

---

### 1-5. 視覚的完了宣言とワーキングメモリの軽量化

未完了のチェックが視界に残り続ける限り、脳はそれを「未処理の項目」として保持し続けようとする。これはワーキングメモリを継続的に消費し、その後の作業に干渉する。

**「気にしないようにする」ではなく「見えなくする」がKoma webの一貫した方針である。**

この原則は以下の形で実装される：

- スタートアップ終了後にエリアをアコーディオンで畳む（未完了Stepが視界から消える）
- 「今日を終了する」で1日の境界線を視覚的に確定する
- 完了済みの項目は操作を受け付けなくなることを明示する

操作を受け付けなくなる＝もう考えなくていい、という認知の切り替えをツール側が担う。

---

### 1-6. ゲーミフィケーションの方向性

モチベーション維持に有効な数値設計の条件：

- **下がらない数字であること**（達成率のような割り算の数字は、失敗で下がりモチベーションを毀損する）
- **加算のみの経験値であること**（見るたびに増えているという事実だけが残る）
- **儀式として機能する確定演出があること**（1日の終わりのボーナス確定が「完了の境界線」を強化する）

## Part 2 | 機能設計

### 2-1. 全体構造

Koma webは**「1日の全行動を包括するダッシュボード」**として機能する。

- コマ（作業単位）の管理
- スタートアップ（1日の設計フロー）
- 定期タスクタブ
- ルーティーンチェック
- 就寝時刻の管理
- 経験値・レベルシステム（外部APIとの連携）

---

### 2-2. スタートアップ（1日を始めるフロー）

旧称「セレモニー」。「スタートアップ」に変更。

**命名の意図：**
「儀式」という重さを持たせず、「1日を起動する」という機能的・実務的なニュアンスを持たせる。ITっぽい語感が設計思想のトーンと合う。

1日を始める際に以下のステップを順番に案内するUIを提供する。ステップごとに「完了」を押さないと次へ進めない設計とし、**工程をサボれないようにする。**

| ステップ | 内容 | xp |
|---|---|---|
| 画面を開く | ログインボーナス（0時〜翌0時で1回） | 10xp |
| 1 | プリセット選択・モード設定 | 10xp |
| 2 | タスク羅列・優先順位設定 | 40xp |
| 3 | 目を閉じて1日を想像する | 30xp |
| 4 | コマごとの設計・事前入力 | 30xp |
| 5 | 机の片付けチェック | 別途（机xpで処理） |
| 全完了ボーナス | 全Step通過 | 20xp |

**スタートアップ合計（ログインボーナス含む・机xp別）：140xp**

**Step2（タスク羅列・優先順位）が最重要工程である意図：**
1日を具体的に設計する工程が集中力と行動効率に最も影響するため、xpを最も高く設定。サボりたくなる工程に報酬を集中させることで、完了動機を強化する。

**スタートアップの終了と0時ロック**

スタートアップには以下の終了条件がある。

| 終了条件 | 挙動 |
|---|---|
| Step5まで全完了 | 自動的にlocked。アコーディオンで畳まれる |
| 「スタートアップを終了する」ボタン押下 | 途中でもlocked。アコーディオンで畳まれる |
| 0時経過 | 強制的にlocked。アコーディオンで畳まれる |

畳まれた状態のヘッダー表示：

| 状態 | ヘッダー表示 |
|---|---|
| 全Step完了 | 「スタートアップ完了 ✓」 |
| 途中終了 or 0時経過 | 「スタートアップ終了済み」 |

**意図：**
未完了のStep項目が視界に残り続けるとワーキングメモリを消費し続ける。アコーディオンで畳むことで視覚的に完了を宣言し、脳がその領域を手放せるようにする。「気にしないようにする」ではなく「見えなくする」という設計思想（1-5）の直接的な実装。

全Step完了と途中終了はヘッダーで区別して表示するが、どちらも畳まれた後は操作を促すUIにはしない。

**0時以降の操作制限**

0時を過ぎたらスタートアップへの入力は受け付けない。操作可能なのは以下のみ：
- 就寝前ルーティーン
- 定期タスク
- 「今日を終了する」

**startup_progress.jsonの構造**

```json
{
  "date": "2026-04-28",
  "completed_steps": [1, 2, 3],
  "locked": false
}
```

dateはクリップボードの日付（セッション日付）を使用。翌日に開いた場合は前日のstartup_progressを引き継がず、新しい日のスタートアップとして扱う。

### 2-3. プリセット・モード設定

毎朝の設定を簡略化するためにプリセットを用意する。

**プリセット初期セット**

| プリセット名 | 目標コマ数 | モード |
|---|---|---|
| 通常 | 6 | 通常モード |
| 休日 | 0 | 休日モード |
| 半休 | 3 | 通常モード |
| 忙しい日 | 6 | 忙しいモード |

**設定項目**
- 目標コマ数
- 休日 / 平日
- 有効にするモードの選択（よく使うものはデフォルトでON）

**モード一覧**
- `忙しいモード`：イレギュラー対応日。コマ追加可。
- `通常モード`（デフォルト）：忙しい廃止中。画面に「忙しい廃止中！」と表示。
- `休日モード`：コマ数0。休日特有のルーティーン・特別タスク（気晴らしに出かけるなど）を表示。

**休日の特別タスク・ルーティーンのxpカテゴリーについて**
休日の行動（外出・気晴らしなど）はworkカテゴリーではなく、mentalカテゴリーへの付与を予定。詳細はmentalカテゴリー実装時に設計する。現時点では「workではないxpカテゴリーが必要」という方針のみ記録。

**「忙しい廃止中！」の表示について**
通常モードでこの文字が常に表示されていることで、忙しいが**例外扱い**になる。意識しなくてもツールが認知を保持してくれる。

---

**目標コマ数について**

デフォルト6コマ。変更が必要になるのは半休・午後の予定が潰れるなどの例外的な場面のみ。予定より時間ができて目標が簡単にこなせた場合も、予定より時間が取れなかった場合も、見積もりの結果として受け入れる。目標は1日の開始時点で確定し、途中変更はしない。

ボードJSONに目標コマ数を記録しておくことで、過去ボードを参照した際に「その日の目標が何コマだったか」を確認できる。

| 要素 | 内容 |
|---|---|
| 全体進捗% | 完了コマ数 ÷ 目標コマ数 |
| 時間軸との照合 | 現在時刻で「ペース的にどうか」を表示 |
| 目標参考ライン | 例：「2時までに50%」など自分で設定可 |

### 2-5. クリップボードUI・日付管理

**UIの構造**
日ごとにクリップボード（ボード）が存在し、ボタンで日付を切り替えて参照できる。

**「今日を終了する」ボタン**

```
[今日を終了する]  就寝時刻: [01:00] ※省略時は現在時刻
[寝ていない]
```

**就寝時刻の判定設計**

| ケース | 挙動 |
|---|---|
| 当日中に終了ボタンを押した | 押した時刻で就寝達成判定 |
| 翌日中に終了ボタンを押した | 就寝時刻入力欄の値で判定。入力時刻と現在時刻の差が3時間超の場合はxp付与なし（記録は残る） |
| 翌々日以降に新しい日を開いた | 前日を自動終了（就寝未達成として処理） |
| 徹夜した | 「寝ていない」ボタンで終了。就寝達成xpは付与されない |

- 押した時点でその日のセッションが確定する
- それ以降のアクションは翌日のボードに帰属する
- 就寝達成xpの判定はこのボタン押下時に行い、リザルト画面に結果を含めて一括表示する

**意図：**
「今日が終わる」という判断を0時という機械的な基準ではなく、人間の行動（寝る前のルーティーンを終えて寝る）に委ねる設計。日付はツールに管理させるのではなく、人間が宣言する。コマ開始時刻を起点にセッションが決まるため、深夜作業で日付をまたいでも意図した日に帰属させられる。

**押せる条件**
- 翌々日以降のボードには存在しない
- 日付をまたいでいるだけの状態（例：深夜2時）なら押せる

**操作権限**
| 状態 | 操作 |
|---|---|
| 当日・翌日 | 読み書き可（ボードJSON更新可） |
| 翌々日以降 | 読み取り専用 |

翌日まで書き込み可にしておく理由：「今日を終了する」を押し忘れたまま寝て翌朝気づいたケースへの対応。

**終了時の統計表示（リザルト）**
「今日を終了する」を押したタイミングで当日の統計を表示する。

| 項目 | 内容 |
|---|---|
| 総獲得xp | 今日の合計・taxonomy別内訳 |
| 完了コマ数 | 目標に対して何コマ |
| 定期タスク | 今日こなしたもの一覧 |
| 就寝時刻 | 目標に対して何分差・達成判定 |
| 連続達成記録 | 就寝達成・全コマ達成など |

**意図：**
1日の終わりに「やりきった」という認知を確定させる儀式として機能する。全コマ達成ボーナスの演出と統計表示が重なることで、終了の境界線がより明確になる。

### 2-6. 日次ボードJSON

スナップショットという特別なファイルは存在しない。**その日のボードを管理するJSONそのものが、当日の状態を保持するファイルである。**

**生成タイミング**
- ページを開いた時点で当日のJSONが存在しなければその場で生成（空の状態）
- 以降はアクションのたびにサーバー側で更新される

**意図：**
「終了時に生成する特別なファイル」という概念を持たない。ページを開けばJSONが存在し、ブラウザはそれをレンダリングするだけ。サーバーが唯一の情報源という原則と完全に一致する。

開かなかった日のJSONは生成されないまま「記録なし」として扱うだけでよく、自動補完や遡及生成の処理は不要。

**「今日を終了する」ボタンの役割**
- JSONの生成とは独立している
- 押した時点でその日のセッションを確定する（以降のアクションは翌日のJSONに帰属）
- 終了時の統計を表示する

**ボードJSONの構造**
```json
{
  "date": "2026-04-28",
  "session_closed": false,
  "routines": [
    { "id": "brush_teeth", "name": "歯磨き", "completed": true, "xp": 30 },
    { "id": "bath", "name": "お風呂", "completed": false, "xp": 30 }
  ],
  "periodic_tasks_done": [
    { "id": "toilet_clean", "name": "トイレ掃除", "xp": 50 }
  ],
  "koma": [
    { "number": 1, "title": "LP作業", "completed": true, "xp": 150 }
  ],
  "startup_completed": true,
  "sleep_achieved": false,
  "total_xp": 1230
}
```

**参照ルール**

| 状況 | 参照元 |
|---|---|
| 当日のボード | 当日のボードJSON（随時更新） |
| 過去のボード | 過去日付のボードJSON（読み取り専用） |
| 記録のない日 | 「記録なし」として表示 |
| 定期タスクの表示判定 | definitions/periodic_tasks.json（現在の設定） |
| ルーティーンの表示 | ボードJSON内のルーティーンリスト（当日生成時にdefinitionsからコピー） |

**ルーティーンをボードJSONにコピーする意図：**
ルーティーンの定義が後から変更・追加されても、過去のボードは生成時点の内容を保持し続ける。現在の設定を参照してしまうと、過去の日に「やっていない項目」が出現して表示が壊れる。

### 2-7. 就寝管理

- 就寝目標時刻を設定（例：1時）
- 6コマ達成後に「完了の境界線」メッセージを表示
  - 「お疲れ様でした」
  - 「就寝まであと○時間○分」
  - 累積就寝達成記録（例：今日達成すれば9日中9回）
- 就寝時刻が近づいたらカウントダウン表示

**残り作業時間の逆算表示**
「今からルーティーンをこなして、残りコマをやって、1時に寝るとしたらあと○分作業できる」
→ 「まだやれる気がして続けてしまう」という判断ミスを防ぐ。

### 2-8. 定期タスクタブ

頻度を設定した定期タスクを管理するタブ。

**表示ロジック**

| 状態 | 表示 | 並び順優先度 |
|---|---|---|
| 本日対象（頻度日数経過） | タスク名 + 実行ボタン | 上位（超過順） |
| 超過あり + スキップ中 | 「スキップ中（○日延長）」 | 中位 |
| まだ期日前 | 「最後に実行：○日前」 | 下位（期日近い順） |

**スキップ機能**

スキップは「今回のみ頻度を延長する」仕様。skip_untilに延長後の日付を書き込む。UIレンダリング時にskip_untilと今日の日付を比較して表示を切り替えるだけで、バックエンドでの定期処理は不要。

| ボタン | 挙動 |
|---|---|
| +1日 | skip_untilを今日から+1日 |
| +3日 | skip_untilを今日から+3日 |
| +7日 | skip_untilを今日から+7日 |
| +14日 | skip_untilを今日から+14日 |
| +周期分 | skip_untilを今日から+frequency_days日 |
| カスタム | 任意入力 |

**+周期分の意図：**
大量に超過タスクが溜まった場合でも、+周期分をポチポチするだけで片付く。「今必要ないタスク」を次のサイクルまで完全に無視したいという意図に最も素直に対応する。

**データ構造**

definitions/periodic_tasks.jsonとhistory/periodic_tasks.jsonをidで結合して使用する。詳細はPart 3参照。

### 2-9. ルーティーンチェック

就寝前のルーティーン（お風呂・歯磨きなど）をチェックボックスで管理。チェックごとに経験値が加算される。プリセットに紐づけて、休日・平日でルーティーンの内容を切り替え可能。

- **順序：任意順**（順番を守ることにインセンティブを持たせない）
- xpはルーティーンごとに個別設定可能。**仮置き：30xp（要調整）**

### 2-10. 机の片付けチェック（スタートアップ Step5）

| 状態 | xp |
|---|---|
| 最初から片付いている or 1分以内 | 80xp |
| 10分以内 | 40xp |
| 10分超 | 10xp |

**意図：**
速いほど良いというフィードバックが、片付けを習慣化するにつれて自然とボーナスが取れるようになるループを生む。

### 2-11. 経験値・レベルシステム

#### アーキテクチャ

**Koma webが持つもの**
- 経験値の付与（APIを叩くだけ）
- 今日の経験値データ（リアルタイム表示・taxonomy別内訳）
- 日ごとの経験値履歴

**Koma webが持たないもの**
- レベル計算・管理
- レベルアップ演出
- ステータス表示
- 全期間の集計・個別検索

**レベル管理システム側（iframeで埋め込み）**
- レベル計算・毎レベルアップ演出を実装する
- もちさんのステータス・現在状況をリアルタイム表示
- 全期間の集計・task_id別検索のAPIエンドポイントを提供

**意図：**
経験値システムを汎用化し、Koma web以外のクライアント（将来的なメンタル経験値・人間関係経験値など）からも同じAPIを叩ける構造にする。Koma固有の概念を経験値システム側に持たせない。

#### 経験値カテゴリー

| カテゴリー | 用途 |
|---|---|
| work | 作業経験値（本ドキュメントの対象） |
| mental | メンタル経験値・休日の行動など（将来） |
| relationship | 人間関係経験値（将来） |

カテゴリーごとに独立したレベル・xp累計を持つ。

#### xp API

```json
POST /api/xp/add
{
  "client_id": "koma_web",
  "user_id": "moti",
  "category": "work",
  "amount": 150,
  "idempotency_key": "moti_koma_2026-04-28_3",
  "meta": {
    "type": "koma",
    "task_id": "koma_3",
    "koma_number": 3
  }
}
```

**metaをtaxonomyの代わりに使う意図：**
経験値システム側はmetaの中身を解釈せず、そのまま保存するだけ。集計クエリはmeta内のフィールドで絞り込む。Koma web以外のクライアントが独自のmetaを持っても干渉しない汎用設計。

#### idempotency_keyの命名規則

```
{user_id}_{type}_{date}_{identifier}

login      → moti_login_2026-04-28
koma       → moti_koma_2026-04-28_3
all_bonus  → moti_all_bonus_2026-04-28
startup    → moti_startup_2026-04-28_step2
periodic   → moti_periodic_2026-04-28_toilet_clean
routine    → moti_routine_2026-04-28_brush_teeth
```

日付はコマ開始時刻ベースのセッション日付（クリップボードの日付）を使用。

**意図：**
同じキーのリクエストは2回目以降を無視することで、ネットワークエラーによるリトライや誤操作による二重付与を防ぐ。個人利用でも履歴の信頼性に直結する。

#### コマxp

| コマ番号 | xp |
|---|---|
| 1〜6コマ目 | 各150xp |
| 7コマ目 | 180xp |
| 8コマ目 | 220xp |
| 9コマ目 | 250xp |
| 10コマ目 | 300xp |

**意図：**
7コマ目以降を漸増させることで、「もう1コマやろう」という動機を自然に作る。

#### 全コマ達成ボーナス

- **条件：** 完了コマ数 >= 目標コマ数（デフォルト6）に到達した瞬間に発火。順不同・飛び番OK。
- **発火タイミング：** 6コマ目到達時（コマ2・6が未完了でも他6つが完了すれば該当）
- **発火回数：** セッションごとに1回のみ
- **xp：** 200xp（レベル管理システム側で演出・一括加算）

**意図：**
全コマ達成ボーナスの演出が「1日の終わりの儀式」として機能する。加算のみの設計思想と組み合わせることで、達成した日が特別感を持つ。

#### 1日のxpシミュレーション

| 条件 | xp |
|---|---|
| ログインボーナス | 10 |
| スタートアップ全完了 | 130 |
| 机（通常） | 40 |
| 6コマ完了 | 900 |
| 全コマ達成ボーナス | 200 |
| ルーティーン3つ（仮30xp×3） | 90 |
| 就寝時刻達成 | 50 |
| **合計** | **1,420xp** |

**1レベル = 1,000xp（線形）**

**線形を選ぶ意図：**
緩やか指数だとレベルが上がりにくくなる後半で「増えている実感」が薄れるリスクがある。加算のみ・上がり続けるという設計思想に最も整合する。

標準日：約1.4レベル/日
定期タスクをこなした日：さらに上乗せ
7コマ以上の日：1.7〜1.8レベル圏
10コマ+全ボーナス：2レベル超

### 2-12. API障害時のxpキュー

API障害時はxp付与リクエストをローカルキューに貯める。

| 項目 | 内容 |
|---|---|
| 障害時の挙動 | ボードJSONへの記録は完了・xp付与APIのみ失敗としてキューに積む |
| キューの保存先 | koma web側のローカル（ボードJSONとは別管理） |
| 再送UI | 「送信待ち」タブに未送信件数を表示・再送ボタンで一括送信 |
| 再送の内容 | xp追加APIを叩くだけ（履歴はすでにボードJSONに記録済み） |
| 二重付与対策 | 再送時も同じidempotency_keyを使用するため二重付与は発生しない |

### 2-13. タスク実行APIとNFC連携

**設計の前提：**
ボードはその日の予定表であり、実行の記録はボードとは独立して機能する。当日のボードに存在しないタスクを実行しても、履歴とxpは必ず記録される。

**タスク実行ページ：**
全定期タスク・ルーティーンのid一覧を取得でき、ボードの状態に関係なく実行を記録できるページを用意する。

| 状況 | 挙動 |
|---|---|
| 当日ボードに存在するタスクを実行 | ボードのチェック状態を更新 + 履歴記録 + xp付与 |
| 当日ボードに存在しないタスクを実行 | ボードは変更しない + 履歴記録 + xp付与 |

**NFC連携：**
定期タスクにNFCタグを物理的に紐づける。タグを読み込むだけでタスク実行APIが叩かれ、記録とxp付与が完了する。

```
NFC読み込み
→ タスクのidをパラメータにAPIを叩く
→ 履歴記録 + xp付与
→ 当日ボードに存在すればチェック状態も更新
```

Koma webを開く・タスクを検索する・チェックを押すという操作をすべて省略できる。NFCはタスク実行APIの最もシンプルなクライアントとして位置づける。（詳細は1-2参照）

## Part 3 | ファイル構成・config設計

### 3-1. ファイル構成

```
data/
  boards/
    2026-04-28.json               // 当日ボードJSON（当日生成・随時更新）
    2026-04-27.json               // 過去ボードJSON（読み取り専用）
    ...
  definitions/
    periodic_tasks/
      toilet_clean.json           // タスクごとの定義（id・name・frequency・xp・frequency_history）
      nail_cut.json
      floor_clean.json
    routines.json                 // ルーティーンの定義のみ（id・name・xp）
  history/
    periodic_tasks/
      toilet_clean.json           // タスクごとの履歴（last_done・skip_flag・skip_until・skip_history）
      nail_cut.json
      floor_clean.json
      archive/
        toilet_clean_2024.json    // 必要に応じてタスク単位でアーカイブ
    startup_progress.json         // スタートアップの進捗（完了Step・date・locked）
config.json                       // Koma本体xp・includeパス・user・api
```

**定義と履歴を分離する意図：**
クローン時はdefinitions/だけコピーすれば新環境として動く。history/は引き継ぐかどうかを選択できる。定義の変更がhistoryに干渉しない。

**タスクごとに個別ファイルを持つ意図：**
全タスクの履歴が1ファイルに集まる構造だと、統計クエリ時に全件スキャンが必要になる。タスク単位でファイルが分かれていれば、特定タスクの統計はそのファイルだけ読めばよい。アーカイブもタスク単位で切り出せるため管理しやすい。

**孤立ファイルの扱い：**
タスクをやめた際にhistory側に孤立ファイルが残ることがあるが、クリーンアップは行わない。historyにのみ存在するファイルは無視する（現行設計のまま）。

### 3-2. config.json

```json
{
  "user": {
    "id": "moti",
    "name": "もちさん"
  },
  "api": {
    "base_url": "http://localhost:3000",
    "xp_endpoint": "/api/xp/add"
  },
  "xp": {
    "login_bonus": 10,
    "startup": {
      "preset_select": 10,
      "task_list": 40,
      "imagination_check": 30,
      "koma_design": 30,
      "completion_bonus": 20
    },
    "desk": {
      "fast": 80,
      "normal": 40,
      "slow": 10
    },
    "koma": {
      "1": 150, "2": 150, "3": 150,
      "4": 150, "5": 150, "6": 150,
      "7": 180, "8": 220, "9": 250, "10": 300
    },
    "all_koma_bonus": 200,
    "sleep_achieved": 50
  },
  "includes": {
    "periodic_tasks": "data/periodic_tasks.json",
    "routines": "data/routines.json"
  }
}
```

**config.jsonの責務：**
Koma本体機能のxp（コマ・スタートアップ・机・就寝）と、各タスクファイルのincludeパス管理のみ。タスク固有の情報は各タスクJSONに持たせる。

**includesを配列にできる意図：**
将来「仕事系の定期タスク」「生活系の定期タスク」を分けて管理したくなったときに、includeパスを追加するだけで対応できる。

### 3-3. 各タスクJSONの責務

タスクごとに定義ファイルと履歴ファイルを1対1で持つ。idがファイル名と対応する。

**definitions/periodic_tasks/toilet_clean.json**（静的・手動編集）
```json
{
  "id": "toilet_clean",
  "name": "トイレ掃除",
  "frequency_days": 7,
  "xp": 50,
  "frequency_history": [
    { "date": "2026-01-01", "frequency_days": 14 },
    { "date": "2026-03-15", "frequency_days": 7 }
  ]
}
```

frequency_historyは「その日付時点での頻度」を手動で記録する。同日複数回変更した場合は最後の値のみ保持。現在のfrequency_daysが最新値。

**history/periodic_tasks/toilet_clean.json**（動的・システムが更新）
```json
{
  "id": "toilet_clean",
  "last_done": "2026-04-28",
  "skip_flag": false,
  "skip_until": null,
  "skip_history": [
    {
      "skipped_at": "2026-04-21",
      "skip_until": "2026-04-28",
      "cancelled_at": null
    }
  ]
}
```

**skip_historyの設計意図：**
スキップした回数・タイミング・期間を蓄積することで、頻度設定の見直しに使える統計データとなる。skip_until期間中に早期実行した場合はcancelled_atに実行日を記録し、「スキップしたがキャンセルした」という事実を残す。

**アーカイブ：**
history/periodic_tasks/archive/toilet_clean_2024.json のようにタスク単位・年単位で切り出す。通常時はアクティブファイルのみ読み込み、統計を出すときだけarchive/を含めて集計する。移動のタイミングは任意（気が向いたときで十分）。

definitionに存在してhistoryに存在しないタスクは初回扱い（last_done: null）として処理する。historyにのみ存在する孤立ファイルは無視する。

### 3-4. xp未指定時のバリデーション

xpフィールドが未指定または不正値の場合：
- 起動時・タスク読み込み時にコンソール・管理画面に警告を表示
- APIは叩く（履歴は残す）
- amount: 0で送信

```
[WARNING] periodic_task "toilet_clean": xp未指定。amount=0で記録されます。
```

**意図：**
xp=0の記録が残ることで「この日のxpがおかしい」と気づけるデバッグの手がかりになる。ファイルを手動で書く前提のため未指定は稀だが、クローン時の設定漏れやtypoへの対策として入れる。

### 3-5. クローン対応

ディレクトリごとコピーしてシステムをクローンできる形式にする。user.id・api.base_urlをconfig.jsonで管理することで、クローン時は該当箇所を書き換えるだけで別ユーザー・別環境に対応できる。

権限・認証方式の詳細設計は実装フェーズで決める（現時点では未設計）。

## Part 5 | 確定済み追加設計

### 5-1. 就寝達成記録のビジュアル表現

**表示要素**

| 要素 | 内容 |
|---|---|
| 連続達成カウンター | 現在何日連続で就寝達成中か |
| 平均持続日数 | 過去の連続記録が途切れるまでの平均日数 |
| コントリビューショングラフ | 日単位のマス目・色で状態を表現 |

**グラフの状態：目標時刻からのずれの絶対値で判定**

早すぎ・遅すぎを同等に評価する。符号付きdeviation_minutesを保存し、グラフ描画時に絶対値で判定する。

| 色 | ずれの絶対値 | 1時が目標の場合 |
|---|---|---|
| 濃い緑 | 0〜30分 | 0:30〜1:30 |
| 薄い緑 | 30〜60分 | 0:00〜0:30 / 1:30〜2:00 |
| 薄い赤 | 60〜120分 | 23:00〜0:00 / 2:00〜3:00 |
| 濃い赤 | 120分以上 | 〜23:00 / 3:00〜 |
| 最も濃い赤 | ― | 寝ていない |
| グレー | ― | 無記録（ボードJSONなし） |

境界値（30・60・120分）は運用後に調整する。

**ボードJSONへの追加フィールド**

```json
{
  "sleep": {
    "target_time": "01:00",
    "target_duration_hours": 7.5,
    "actual_time": "01:40",
    "deviation_minutes": 40
  }
}
```

target_duration_hoursは季節によって変更する可能性があるため、その日の目標値をボードJSONに記録しておく。deviation_minutesは符号付き（早い場合はマイナス）で保存。
